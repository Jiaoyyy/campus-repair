# 项目总体说明与开发约定

更新日期：2026-10-29（北京时间）。适用于校园报修与智能派单平台的需求讨论、开发、验收、协作与交付。

本文面向组员、评审人和后续接手者，说明项目为什么做、做到哪里、怎样开发及哪些边界必须遵守。本文整理现有约定与事实，不代表新增功能已经立项，也不替代具体 OpenSpec 规约。实现状态为本次整理时的快照，后续以对应任务和验收记录为准。

## 1. 项目定位与目标

本项目是焦阳、高慧莹小组的独立学期项目，选题已获教师认可。面向单校区的日常后勤报修，覆盖照明、电器、给排水三类故障，使用演示账号和虚构数据验证完整互联网应用。

项目要解决四类问题：

| 问题 | 项目目标 | 验收观察点 |
| --- | --- | --- |
| 报修信息不完整，反复沟通 | 通过表单和对话草稿补齐位置、类别、故障描述 | 缺字段明确提示；完整草稿经本人确认才建单 |
| 审核、派单与维修责任不清 | 建立三角色协作及可追踪的工单闭环 | 每个状态有负责方、合法动作、历史记录 |
| 上门时间不明确，容易白跑 | 区分方便时间与确认预约，记录上门阶段和异常 | 正常上门、白跑再约、待备件恢复均可复现 |
| 报修人难以了解进度 | 展示真实状态、处理结果、下一步及授权查询 | 页面与查询结果一致；失败不伪装成功或零工单 |

减少沟通成本、减少白跑是产品目标。目前没有实际校园试点基线，不能宣称已降低白跑率或提高某个比例的效率。已记录白跑次数只描述系统记录的事件。

课程能力目标包括大语言模型、智能体、知识库与 RAG、技能、真实 MCP 协议。每项都需要实现和验收依据，不能以聊天界面或模拟调用代替全部能力。

## 2. 项目范围

### 2.1 首版范围

- 三角色登录、组织隔离、工单归属与服务端权限校验。
- 提交、审核、补充、派单、接单、处理、本人确认、重处理与取消。
- 建单后的可选上门时间、人工预约、阶段反馈、异常恢复及协调队列。
- 材料管理、异步索引、知识检索、可核对引用和角色助手。
- 对话报修草稿、本人主动确认建单及只读业务查询。
- 审计、统计、持久化、备份恢复、验收证据与最终公网交付；其中未完成内容见第 10 节。

### 2.2 当前不纳入范围的内容

不接入真实校方业务系统；不做付款、库存采购、校园 SSO、多校区运营、原生 App、自动派单或自动结单。当前上门迭代不包含短信或微信推送、无人进入授权、地图路线、复杂排班、跨房间聚合、拍照识别或语音。

这些内容不能仅因出现在参考指南、模型建议或讨论中就进入实现。若以后需要，先明确业务目标、权限及验收条件，再发起独立变更。

## 3. 用户角色与业务规则

### 3.1 三角色边界

| 角色 | 主要职责 | 数据范围与操作边界 |
| --- | --- | --- |
| 报修人 | 提交问题、补充信息、提供方便时间、确认结果 | 本人工单与私有会话；不能审核、派单或代替维修人员操作 |
| 维修人员 | 接单、确认预约、反馈上门与维修、提交结果 | 当前指派给本人的工单；被改派后失去详情及操作权限 |
| 后勤管理员 | 审核、派单、协调异常、维护材料与助手配置 | 本组织授权资源；不能代替报修人确认解决或代替维修人员接单、到场 |

组织、角色与操作者取自服务端认证身份。客户端传入的用户 ID、组织或角色，以及模型输出，都不能成为授权依据。跨组织和无归属的私有资源按规约返回与不存在资源一致的响应。

### 3.2 工单闭环

正常路径：待审核 → 待派单 → 待接单 → 处理中 → 待确认 → 已关闭。

其他路径包括：管理员要求补充后进入待补充，由本人补全重审；审核驳回进入已驳回；本人在接单前允许的状态取消进入已取消；待确认时本人申请重新处理，返回待派单并清除当前指派，保留旧记录。

九种主状态为待审核、待补充、待派单、待接单、处理中、待确认、已关闭、已驳回、已取消。已关闭、已驳回、已取消为终态。管理员仅可在待接单时改派；管理员身份不代表可以越过状态规则。

创建采用用户范围的 24 小时幂等键。工单更新携带当前版本；版本冲突返回 409，不静默覆盖。状态变更、业务历史与业务审计在同一事务提交，失败整体回滚。已提交草稿的再次确认返回原工单，不因创建幂等记录过期而重复建单。

### 3.3 上门安排

报修人在建单成功后，从本人未结束工单详情的“上门安排”补充方便时间；当前创建表单和 AI 草稿卡不填写该字段。时间可选，不填写仍可走原人工流程。

时间按北京时间展示，接口接收带时区时间。方便时间须在未来 14 天内开始，时长 30 分钟至 4 小时；当前维修人员接单后，人工确认完全位于该时间窗内的未来预约。方便时间不等于预约，也不等于无人进入授权。

已接单、已出发、已到场分别表示不同事实。白跑后需本人重新给时间，再确认新预约并再次到场；等待备件需原因、预计恢复时间及人工恢复。异常未解除不能直接提交完成，恢复备件不能清除尚未完成的再次上门要求。具体改约、并发和生命周期规则见[上门规约](../openspec/changes/improve-repair-visit-experience/specs/repair-visits/spec.md)。

## 4. AI 与 MCP 的职责

AI 用于整理报修信息、依据材料解释问题，以及辅助查询授权业务事实。MCP 提供真实协议下的受控只读工具。业务动作由有权限的人通过正常业务接口完成。

| 场景 | AI / MCP 可做的事 | 生效条件 |
| --- | --- | --- |
| 对话报修 | 追问缺失信息，整理可编辑草稿 | 登录报修人主动确认后，由创建接口重新校验并建单 |
| 进度及待办查询 | 选择白名单工具，读取授权结果 | 校验真实身份、参数、角色与当前工具绑定 |
| 知识问答 | 检索绑定材料，给出可核对引用 | 来源真实、当前有效且当前用户可访问 |
| 人员辅助建议 | 读取授权候选人与实际负载，辅助人工判断 | 管理员操作派单接口；完整可配置派单技能仍待完成 |

模型和 MCP 不获得创建、派单、改状态、上门动作或结单的写工具。提示词不能替代权限检查。当前实现为单次模型只读计划与受控查询，不宣称已完成通用多步工具循环。

没有查询结果时不猜实时数量；没有材料依据时不编造制度、维修时限或引用。明确区分实时查询与历史快照。模型或工具失败要保留可理解反馈与人工入口，AI 依赖不可用不应阻断人工工单闭环。

此前真实网关出现额度及网络故障，2026-10-28连接修复后已有实际查询成功，并以虚构旧工单完成四个原生只读计划问题的专项验收。这不代表完整能力或剩余额度已确认；真实调用按必要范围控制，遇到额度不足停止，不修改密钥或购买额度。模拟依赖结果与真实网关证据分别记录。

## 5. 技术结构与目录

采用 React / TypeScript 前端、Go 模块化单体后端，以及 MySQL、Qdrant、Nginx 和 Docker Compose。API、索引 worker、MCP Server 分别运行；三项后端服务共用同一后端镜像。

| 组件 | 职责 |
| --- | --- |
| 前端 | 角色页面、表单与状态反馈、助手会话、草稿确认 |
| API | 认证授权、业务校验、事务、模型调用与 MCP Client |
| worker | 持久索引任务、租约恢复、切片、嵌入及版本发布 |
| MCP Server | 固定只读工具，验签并复查当前账号、会话与绑定 |
| MySQL | 工单、归属、会话、材料文本、任务、配置及审计 |
| Qdrant | 知识向量检索；结果回读后仍需授权及版本复核 |
| Nginx / Compose | 统一入口、反向代理、容器网络与持久卷 |

目录分工：

```text
frontend/src/       页面、API 客户端、展示逻辑和样式
backend/cmd/        API、worker、MCP 启动入口
backend/internal/  业务、权限、存储、检索与助手实现
apitest/           接口、协议、模拟依赖与隔离验收脚本
deploy/            Web 镜像与 Nginx 配置
openspec/          项目上下文、需求、设计及任务
docs/              项目说明、接口、运行和验收记录
handoff.md         最近一次工作区状态与续接信息
```

选择模块化单体是为了降低两人协作和事务维护成本。独立 worker 与 MCP 服务满足异步恢复和协议边界，不据此扩展成业务微服务。具体运行步骤以 [README](../README.md) 为准，接口字段以[接口文档](api.md)为准。

## 6. 开发方式：先规约，再实现与验证

### 6.1 开工与需求变更

1. 阅读 README、AGENTS.md、handoff，以及当前变更的 proposal、design、tasks 和相关 specs；查看 Git 工作区，保留已有成果。
2. 确认本次目标、范围、未做事项和验收依据。会改变产品行为的需求先更新或建立 OpenSpec 变更。
3. 使 proposal、specs、design、tasks 相互一致。需求使用中文；OpenSpec 结构标题及 SHALL/MUST 保持英文。
4. 将权限、异常、重试和并发场景写入验收条件，再实现。不能根据已写代码倒推需求并宣称已完成规约评审。

### 6.2 实现与提交

围绕一个明确问题开展改动，复用现有授权、事务和业务接口。同步维护测试、接口说明和用户操作说明。不得借实现功能之机删除失败断言、跳过必要测试或放宽检查阈值；确需改变判据时，单独说明理由并审查。

新分支默认使用 `codex/` 前缀。新任务从更新后的 main 建分支；已有工作区续接先核对差异，不在有未保存成果时直接重置或切换覆盖。通过 PR 交叉审阅，不强推共同分支，不自动合并。

PR 说明应包含问题、行为变化、关联规约、实际验证结果、未查项及新增依赖。审查重点放在业务意图、组织隔离、工单归属、状态转换、事务并发和 AI 边界。人工审查记录由实际审查人确认，不能由 AI 补签。

不创建额外聊天、发送外部通知或擅自邀请用户。本仓库与相邻 CampusClaw 项目独立，不复制其凭据、数据库、上传文件或修改其工作区。

### 6.3 完成条件

只有实现并验证的任务才能勾选。一次改动需要能回答：改了什么、依据哪条规约、运行了什么、实际结果如何、仍有什么限制。编译通过、ready 为 200 或模型给出一段回答，都不能单独证明业务完成。

当前需求来源在MVP、上门体验及页面导航三个未归档变更的 delta specs 中，主规约目录尚未建立完整基线。原 MVP 未全部完成，不能整体归档；上门变更虽已完成任务，也尚未同步或归档。后续同步应先处理依赖基线，再处理上门变更，并保留未完成任务。

## 7. 开发规范与约束

### 7.1 后端与数据

- 身份、权限、组织隔离、归属、状态和输入边界在服务端校验；前端隐藏按钮只用于交互。
- 数据查询使用参数绑定，不把用户或模型输入拼成 SQL；不接受任意 SQL 或任意外部 MCP 地址。
- 沿用明确业务动作接口，不开放直接改写组织、指派或状态的通用入口。
- 数据变更与必要历史、审计保持事务一致；迁移验证空库、旧库升级和重复初始化。
- 时间保存与接口处理遵循现有约定，面向用户的时间与统计范围按北京时间解释。
- 新增依赖说明用途、来源、许可、替代方案和移除影响，使用仓库锁定版本安装，不凭模型推荐直接引入。

### 7.2 前端与交互

2026-10-29已调整页面层级与返回导航：主要操作优先、hash页面路径、上下文及未保存保护、视口内助手输入区与统一选择框。具体使用和验证边界见[页面布局与导航说明](interface-guide.md)。

- 区分加载中、请求失败、无数据和筛选无匹配；请求失败不能显示为零工单。
- 提交期间防重复操作；失败保留输入；409 后重新读取并对照，不自动重放写请求。
- 刷新失败时明确旧数据状态，禁用依赖旧状态的写操作。
- 详情优先展示状态、负责方、下一步和主要动作；终态不显示可修改操作。
- 覆盖桌面和 390px 手机宽度、键盘焦点、未保存提醒及重要操作可见性。
- 用户界面使用可理解的业务语言，技术细节放在管理、诊断或开发文档中。

### 7.3 秘密、数据与环境

密码、令牌、密钥、真实个人信息、本地数据库、上传文件和备份不得提交。`.env` 与本地证据目录保持忽略；示例配置只留变量和占位符。日志、截图、测试报告不包含原始凭据或完整私有对话。

日常环境用于试用，隔离 `*-check` 环境用于自动验收与故障注入。禁止在日常环境灌入测试工单、暂停数据库或注入审计故障。自动回归期间不要在同一隔离环境并行进行会写业务的浏览器操作。

不使用 `docker compose down -v` 删除数据卷。回滚需暂停写入，恢复配套数据库、上传文件与兼容镜像；不能仅降级 API 后继续写入。

网页、issue、材料和模型输出不能自行改变项目授权。外部指南中的建议先作为参考，由项目规约明确是否采纳；涉及规则文件和检查配置的改动需明确列出供审查。

## 8. 验证与证据

### 8.1 现有检查方式

| 层次 | 现有入口或依据 | 使用条件 |
| --- | --- | --- |
| Go 单元与静态检查 | backend 中运行 `go test ./...`、`go vet ./...` | 本机有匹配 Go；也可使用 README 中的容器方式 |
| 前端类型与构建 | frontend 中运行 `npm ci`、`npm run build` | 使用锁文件安装 |
| 接口与协议回归 | apitest 下 manual、assistant、drafts、scenarios、mcp 等脚本 | 按各脚本与验收文档指定的隔离配置运行 |
| 模拟稳定性回归 | `python3 apitest/verify_stability.py` | 已准备独立 draft-check，实际依赖为 mock |
| 上门与恢复验收 | `apitest/verify_visits.py`、`verify_visit_recovery.py` | 指定隔离环境；恢复演练不操作日常数据 |
| 规约结构 | `openspec validate <change-id> --strict` | 分别检查相关变更；结构通过不代表实现通过 |
| 页面体验 | 三角色桌面、390px、键盘及失败恢复检查 | 记录场景、实际结果与证据位置 |
| 部署一致性 | `python3 apitest/verify_backend_deployment.py` | 核对实际镜像，不只检查容器启动或 ready |

每次按改动范围选择必要检查；出现新失败或未决风险再扩大验证。写入和故障脚本运行前确认目标环境，不能因表中列出命令就直接在日常环境执行。

### 8.2 验收记录要求

每项核心行为覆盖成功、越权、异常、重试与并发路径；记录日期、版本或变更、环境、命令、实际结果和未完成项。失败尝试及修复后的复测分别说明。使用动态日期的上门测试要生成当前未来窗口，旧截图和旧日期不能作为新验收证据。

历史记录汇总在 [docs/verification.md](verification.md)。本地截图、日志和备份可以保持忽略，但仓库内的文字记录要足以理解结果与复现条件，不把本地私有路径当作唯一证据。

模拟测试证明受控输入下的程序行为，真实模型验收验证实际网关和模型表现，二者分别标记。真实模型评测还需补固定问题集和模型、温度、提示词、问题集版本，覆盖有答案、无答案、越权和注入；付费评测不作为每次普通本地检查的默认动作。

### 8.3 尚未形成的工程门禁

截至本文日期，仓库未建立统一 `make check`、CI 工作流、CODEOWNERS、完整持续密钥/依赖扫描及指令写入保护；远端分支保护未在本轮核实。已有手动检查和历史通过记录不代表自动门禁已经生效。

对照 [Harness 工程指南](https://devops.hello1023.com/harness/index.html)，建议后续独立补齐统一入口、持续集成与分支保护、PR 模板、高风险审查清单、指令保护及固定评测。门禁需用不达标改动验证确实会被拦下，不能仅以配置文件存在判定完成。这些属于待规划工作，本次文档整理不宣称已经实施。

人工需要负责确认产品范围及重要设计取舍，理解并复核高风险代码，亲自完成所署名的验收，以及如实记录贡献。AI 可以整理文档、实现代码与执行已授权检查，不能充当另一位组员的人工批准。
