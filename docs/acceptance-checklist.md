本文是待执行清单，不是通过报告。全部复选框初始未勾选；每项执行后记录“通过 / 失败 / 阻塞 / 未执行 / 不适用”，通过时再勾选。历史测试结果见[验收记录](verification.md)，不能直接搬成本次结果。后续需求改变时同步扩充用例。

## 0. 使用方法与执行环境

| 标记 | 谁执行、在哪里执行 |
| --- | --- |
| R | 人工只读审核：当前日常预览可做，不修改原工单、材料或配置 |
| W | 人工完整流程：只在已确认的独立 `*-check` 环境，用虚构工单和材料执行 |
| E | 工程验收：接口、协议、模拟时钟、故障、并发或安全测试，只在独立 `*-check` 环境 |
| T | 尚未完成或需另行确认的目标：记录缺口，不能当作现成功能打勾 |

日常预览为 `http://127.0.0.1:18083/`。历史隔离预览为 `http://127.0.0.1:18086/`，但端口本身不能证明隔离：执行 W/E 前核对 Compose 项目名、数据库/上传卷、模拟依赖与实际镜像。不要把隔离环境密码用于日常环境，反之亦然。

已于2026-10-29准备专供你人工审核的[18087验收数据环境](review-data.md)：80张虚构工单、10种上门场景、4份材料及本地账号文件。W类优先在此执行；批量自动回归和E类故障注入仍用其他独立环境，避免破坏人工审核基线。该环境使用真实模型配置，不把人工问答当作mock。

使用 README 中的管理员、两个报修人、两个维修人员和隔离组织账号；密码从对应本地环境配置读取，不贴进文档或截图。多角色用独立浏览器上下文或分别登录，测试前先确认界面显示的角色。

真实模型查询会消耗网关额度。程序与故障用例优先使用 mock；实际模型评测单独记录模型、参数、提示词版本、问题集、调用数与环境。网关已失败时不连续重问，不买额度、不更换凭据来凑“通过”。

所有涉及写入、关闭服务、禁用账号、故障注入、限流、迁移和恢复的用例都不得对日常环境执行。自动回归期间不同时在同一隔离环境写业务。本文不提供删除数据卷的测试动作。

## 3. 登录、身份与会话

- [ ] AUTH-01【W】三角色正确登录 → 进入各自入口；维修人员默认进入维修工作台。
- [ ] AUTH-02【W】错误密码与不存在账号各测试一次 → 相同状态与通用错误，不透露账号存在性。
- [ ] AUTH-03【W】登录后刷新 → 有效会话可恢复，角色不改变；不把密码或令牌放进URL。
- [ ] AUTH-04【W】退出后刷新、后退及重新读取受保护数据 → 不继续取得新业务数据。
- [ ] AUTH-05【E】缺失、伪造、过期和已登出令牌分别访问 → 401，无业务副作用。
- [ ] AUTH-06【E】账号禁用后重用旧登录 → 会话失效；恢复账号不自动恢复已撤销令牌。
- [ ] AUTH-07【E】只带Cookie、不带Bearer访问受保护接口 → 不能取得认证访问权限。
- [ ] AUTH-08【E】一分钟同来源失败达到阈值后继续登录 → 429及重试时间；仅隔离环境测试。
- [ ] AUTH-09【E】不存在账号的登录路径 → 仍执行虚拟密码哈希比较，响应/日志不暴露账号存在性。
- [ ] AUTH-10【W/E】多个独立登录上下文切换角色 → 当前标签页不串号，不显示上一用户私有会话。

## 4. 人工工单闭环与输入

### 4.1 提交、审核与补充

- [ ] ORDER-01【W】报修人填写位置、三类合法类别和描述后提交 → 唯一编号、待审核、本人和本组织管理员可查看。
- [ ] ORDER-02【W】分别遗漏位置、类别、描述，或输入纯空格 → 明确字段错误，不创建空单。
- [ ] ORDER-03【E】位置200/201字、描述2000/2001字及中文/emoji边界 → 合法边界接受，超限拒绝且无半条记录。
- [ ] ORDER-04【E】未知类别、身份字段、非法JSON、超长请求 → 按接口契约拒绝，不按默认类别偷偷创建。
- [ ] ORDER-05【W】管理员审核通过 → 待派单，时间线记录真实操作者与动作。
- [ ] ORDER-06【W】管理员填写原因要求补充，本人修改后重新提交 → 待补充→待审核，原要求和补充历史保留。
- [ ] ORDER-07【W/E】非本人补充、在非待补充状态修改原报修字段 → 拒绝，不覆盖原信息。
- [ ] ORDER-08【W】管理员填写原因驳回 → 已驳回；空原因拒绝，驳回后无恢复或修改入口。

### 4.2 派单、接单与结单

- [ ] ORDER-09【W】管理员给待派单选择本组织、启用且类别匹配人员 → 待接单，双方看到同一指派。
- [ ] ORDER-10【E】选择跨组织、禁用或类别不匹配人员 → 拒绝，原状态和历史不变。
- [ ] ORDER-11【W】待接单时填写原因改派 → 新人员可见，旧人员失去详情权限；历史保留。
- [ ] ORDER-12【W/E】处理中改派或管理员代替接单 → 拒绝，不放宽原状态规则。
- [ ] ORDER-13【W】当前被指派人员接单 → 处理中；其他维修人员不能接单。
- [ ] ORDER-14【W】添加处理记录，填写措施与结果后提交 → 待确认，记录可核对；空措施/结果拒绝。
- [ ] ORDER-15【W】本人确认解决 → 已关闭；管理员和维修人员不能代替确认。
- [ ] ORDER-16【W】本人填写未解决原因申请重处理 → 待派单，清除当前指派，旧维修结果与历史保留。
- [ ] ORDER-17【W】本人在接单前允许状态填写原因取消 → 已取消；处理中取消拒绝。
- [ ] ORDER-18【E】已关闭、已驳回、已取消上重复动作或尝试恢复 → 拒绝，版本、事件及预约不被改写。
- [ ] ORDER-19【W】按全流程刷新并重新登录查看 → 原始信息、状态、负责方、结果和历史一致。
- [ ] ORDER-20【W】不使用AI、不填写上门时间走完整人工闭环 → 正常完成，不依赖模型网关。

## 5. 上门安排与异常恢复

- [ ] VISIT-01【W】建单后从详情补方便时间 → 入口可发现；创建表单/草稿未填时间不阻断报修。

- [ ] VISIT-04【W/E】过去时间、起止颠倒、缺少一端、无时区、非法日期 → 拒绝并保留输入，数据不变。
- [ ] VISIT-05【W】当前维修人员接单后确认偏好内预约 → 双方显示相同北京时间；管理员不能代替确认。
- [ ] VISIT-06【E】无有效偏好、超出偏好、待接单或异常未解除时确认 → 拒绝，不伪造预约。
- [ ] VISIT-07【W】本人修改已确认但未出发安排 → 要求原因并说明旧预约将失效；成功后等待重新确认。
- [ ] VISIT-08【W】修改后重新确认 → 原预约历史保留，同一时刻只有一个有效预约。
- [ ] VISIT-09【W】依次出发→到场 → 阶段及实际发生时间正确；接单不冒充出发，到场不表示进入房间。
- [ ] VISIT-10【E】重复出发、先到场后出发、重复到场 → 409，事件不重复。
- [ ] VISIT-11【E】预约已过期而尚未出发 → 不允许出发；此前已出发则允许迟到到场并保留事实。
- [ ] VISIT-12【W/E】出发或到场后本人直接改方便时间 → 拒绝，先按异常流程处理。
- [ ] VISIT-13【W】到场后填写原因记录报修人不在 → 待重新约时，原预约失效，白跑只记一次。
- [ ] VISIT-14【W】白跑后直接提交完成 → 拒绝；须本人新时间→新预约→再次到场后再正常处理。
- [ ] VISIT-15【W】记录等待备件 → 原因、未来预计恢复时间必填，主状态仍为处理中，有效预约撤销。
- [ ] VISIT-16【W/E】等待备件时直接提交完成，或仅等待预计时间过去 → 仍不可完成，不自动恢复。
- [ ] VISIT-17【W】当前维修人员填写说明恢复备件处理 → 保留异常历史；是否需要重新上门按真实记录判断。
- [ ] VISIT-18【W/E】先白跑后待备件、先备件后白跑分别验证 → 恢复备件不清除尚未完成的再次上门要求。
- [ ] VISIT-19【W/E】改派、重处理、取消、驳回、提交结果、关闭 → 当前预约结束且历史保留；不得自动复活旧预约。
- [ ] VISIT-20【W/E】非本人、原维修人员、他组织读取/修改上门 → 404或规定的角色拒绝，不泄漏新安排。

- [ ] VISIT-22【W】每次操作后双方分别刷新 → 读取时间与阶段一致，不声称已经发送短信或获得无人进入授权。

## 7. AI查询专项：问法、范围和证据

下列每个独立问题从新对话开始；标注“连续”的按顺序在同一对话执行。对照六条基线或当次实际授权列表判断，不以语气流畅判通过。R可做日常只读核对，精确计数及故障请用W/E。

### 7.1 楼栋、状态与关键词

- [ ] AI-01【R/W】“研发楼有什么问题” → location为研发楼，不限日期；专用基线为Q1–Q4共4单。
- [ ] AI-02【R/W】“研发楼一楼怎么了” → 仅一楼，不限日期；基线Q1/Q4共2单。
- [ ] AI-03【R/W】“研发楼有哪些未解决问题” → 未结束、不限日期；基线Q1/Q2/Q4共3单，不含已关闭Q3。
- [ ] AI-04【R/W】“研发楼最近有什么故障” → 最近含今天7天创建日期；基线Q3/Q4共2单，不能偷偷补旧单。
- [ ] AI-05【W】准备仅有14天前未结束记录的楼栋，再问最近 → 真实0条、有日期范围和旧单提示；再独立问有什么问题应命中旧单。
- [ ] AI-06【R/W】“研发楼有哪些漏水报修” → 位置与漏水描述同时匹配，不把漏水自动扩大成整个给排水类别；明确问给排水类别时才按类别筛选。

- [ ] PERF-05【W】Chrome与另一种可用浏览器、手机浏览器分别走关键路径 → 日期控件、流式消息和焦点差异有记录；不可用浏览器写未执行。
- [ ] PERF-06【W】浏览器缩放至200%、长文本和软键盘 → 记录可读性及主操作可达性问题，不把桌面截图替代手机验收。

## 17. 如何记录结果与判定本轮审核

每个失败独立记录，不用“AI不灵”“点了没反应”代替复现条件。建议按下表复制填写：

| 字段 | 填写内容 |
| --- | --- |
| 用例编号 / 结论 | 如AI-01；通过、失败、阻塞、未执行、不适用 |
| 日期 / 验收人 / 环境 | 北京时间、实际执行人、端口及Compose项目；mock或真实 |
| 版本 / 浏览器 | 提交及未提交差异或镜像ID；浏览器/视口 |
| 前置条件 | 角色、状态、基线记录、是否新对话；不得填密码/令牌 |
| 操作原文 | 完整输入、点击顺序、连续追问顺序 |
| 预期 / 实际 | 数量、筛选、状态、提示；不要只填“正常” |
| 证据 | request_id、脱敏截图、脚本结果与相关规约；私有日志保持本地 |
| 缺陷及复测 | 严重度、复现频率、修复版本、复测结果；失败记录保留 |

- [ ] CLOSE-01【W/E】关键结果有独立依据 → 助手对列表/接口，状态对事件，统计对全量数据，不拿同一段模型回答自证。
- [ ] CLOSE-02【W/E】成功、越权、异常、重试、并发均有覆盖或明确未执行 → 未执行不算通过。
- [ ] CLOSE-03【W/E】无未解决的越权、泄密、错误建单/状态、数据丢失、伪造查询成功等阻断缺陷 → 有则本轮审核不通过。
- [ ] CLOSE-04【W/E】测试后恢复助手配置、mock模式及临时停用服务 → 不把日常系统留在验收配置。
- [ ] CLOSE-05【W/E】人工读过关键业务与权限路径，并记录姓名、日期、依据 → AI运行测试不能代替人工签字。
- [ ] CLOSE-06【W/E】已实现/未实现、mock/真实、历史/本次结果分别说明 → 不因某组脚本全绿就宣称全系统通过。

本轮结论可分别为“当前界面审核通过”“某变更验收通过”“仍有阻断缺陷”或“完整交付未完成”。只有在所声明范围内必测用例完成、阻断问题清零且证据齐全时，才能给出对应通过结论。
