## 从哪里开始操作三角色流程

1. 用`admin`进入报修管理，可筛待审核、待派单，验证审核、要求补充、驳回和派单；矩阵S01–S18可作为起点。
2. 用`requester`或`requester2`处理本人的待补充和待确认，验证补充重审、确认关闭、申请重新处理；账号不同不能处理对方的记录。
3. 用`tech`或`tech2`登录，默认进入维修工作台，验证接单、维修记录、提交结果及上门动作。
4. 用`other`或`other_admin`核对隔离组织数据，再尝试本组织Q1编号，应不可见。
5. 对照本地目录中的真实工单号和位置寻找记录。列表目前按位置筛选；不要把S01等内部验收标签误当成工单编号。

本次还给`requester`保留了一个真实生成的可编辑报修草稿示例。打开助手中“三号楼201，照明灯完全不亮，帮我报修”会话可继续编辑或确认。准备时没有点击确认，也没有创建第81张工单；你主动确认后基线数量会增加。

## 上门场景

所有V工单主状态都是处理中。奇数V由requester报修并指派tech；偶数V由requester2报修并指派tech2。

| 编号 | 当前场景 | 推荐验证 |
| --- | --- | --- |
| V01 | 无方便时间、无预约 | 本人补时间，维修人员再确认 |
| V02 | 只有明天的方便时间 | 区分时间偏好与预约，维修人员确认 |
| V03 | 已确认未来预约 | 本人改约需原因、旧预约失效；或维修人员出发 |
| V04 | 已出发 | 本人不能直接改约，维修人员可以到场 |
| V05 | 已到场 | 记录处理结果，或记录报修人不在 |
| V06 | 已记录白跑，待重新约时 | 本人提供新时间→新预约→再次到场；直接完成应拒绝 |
| V07 | 等待备件 | 当前维修人员填写恢复说明，预计时间过去不自动恢复 |
| V08 | 白跑后又等待备件 | 恢复备件后仍保留重新上门要求，不能直接结单 |
| V09 | 昨日预约逾期、未出发 | 管理员协调队列可见；不能对过期预约直接出发 |
| V10 | 已出发但昨日预约已逾期 | 仍计逾期，允许记录迟到到场并保留事实 |

准备时管理员协调数量为：逾期2单、待重新约时1单、待备件2单。V06和V08各记录一次白跑，近7天已记录白跑共2次。日期和人工操作会改变今日/逾期数量。

## 再次启动与核对

已有本地配置和镜像时，在仓库根目录执行：

```sh
python3 apitest/prepare_review_data.py
```

首次准备环境和数据；以后只启动现有环境、登录读取并核对，不重置你改过的工单、配置或预约。纯核对可执行：

```sh
python3 apitest/prepare_review_data.py --verify
```

已经实际给S25增加处理记录再重复准备，确认版本、记录及七张业务表摘要均保留。未知同名资源、被占端口、共享数据卷或误指日常项目会拒绝，不自动删除或覆盖。

本工具没有自动清库/重置选项。不要在本环境运行批量回归或故障注入；这些另用draft-check等工程环境。服务普通停止后保留卷，重新启动不会恢复成初始状态。跨天后新时间测试使用当前未来窗口；旧预约变成逾期是正常事实，不应自动改写原数据。

本机账号、完整配置、实际目录和检查结果在Git忽略的 `tmp/review-check/`，账号及配置权限600。不要提交这些文件、上传或数据库。完整审核仍按[238项测试清单](acceptance-checklist.md)执行；这次完成的是数据准备与基础核对。
