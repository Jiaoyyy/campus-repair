# Proposal

## Why

当前所有维修提交都进入待确认，报修人未操作时没有关闭时限。未解决申请统一清空指派并返回管理员派单，可能给同一故障多加一次交接。另已复现方便上门时间过期后的重约断点。应减少没有新增判断价值的操作，并保留能纠正维修结果和跟踪责任的路径。

## What Changes

- 拟按维修结果是否可在现场验证、是否存在未解除异常区分关闭路径。现场可验证的常规维修允许授权维修人员一次提交完成；需要报修人验收、或需观察的工单保留主动确认。
- 为允许超时结束的待确认工单定义截止时间、结果可见性、系统关闭记录和关闭后的反馈路径。时间、适用判定及必须主动验收的边界待产品确认。
- 对仍未解决且原维修人员适配、可继续负责的工单，优先原单继续处理。只有确实需要换人时才进入派单队列。补齐过期上门窗口后的重约路径。
- 审核与派单保留可分别完成的入口。已有充分信息且人员可选时评估管理员一次确认审核并派单，保留两步各自的记录。

## Capabilities

### New Capabilities

- `repair-workflow-efficiency`：维修完成、超时关闭、继续处理及低重复交接的准入和审计规则。

### Modified Capabilities

落地前同步修订仍生效的 `build-campus-repair-mvp` 中的 `repair-work-orders` 与 `improve-repair-visit-experience` 中的 `repair-visits` / `repair-workbench` 规约。当前变更是提案，既有“首版无自动结单”规则继续作为当前验收依据。

## Impact

涉及工单状态转换、关闭依据与截止时间、任务队列、上门重约、历史记录、审计及只读 MCP 展示。AI 和 MCP 权限沿用只读边界。存量待确认工单保持原规则，后续迁移时需明确启用范围。
