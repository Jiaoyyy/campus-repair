# Design

## Context

- 强制确认：`model.go` 中每次 `complete` 都进入 `awaiting_confirmation`，仅本人确认才会关闭。目前队列把待确认算作报修人待办，worker 仅运行材料索引。
- 重复派单：`store.go` 中 `reopen` 总是清空当前指派。若同一维修人员仍能处理，管理员仍需再次派单，维修人员也需重新接单。
- 重约断点：`visits.go` 中过期且未预约的偏好已不满足 `schedule`，也没有维修人员请求新时间的动作。`visit_workbench.go` 的重约查询只含已有白跑异常。见 [隔离复现](../../../docs/verification.md#2026-11-19-审计统计与工具故障边界)。
- 重复审核：待补充重新提交后统一回到待审核。位置、类别或故障发生实质变化时重新核对合理。纯附加说明是否可少操作，需要用实际样例复核，首批保留原审核。
- 审核和派单：现在是独立的管理员动作。没有匹配维修人员时独立审核有意义，能够现场选定人员时可评估一键完成。

## Goals / Non-Goals

**Goals:** 减少常规维修对报修人的追单、同故障的重复派单，以及上门偏好过期后靠人发现的空转。所有保留的人工作业都应对应一个真实的判断或处置。

**Non-Goals:** 不做全量历史补关、不以故障大类或 AI 推断风险、不增加默认催办任务或人工审批层级，也不自动派单。

## Decisions

1. 先确定完工路径与判定依据。经现场验证且无阻塞的可在提交维修结果时关闭。需观察且允许超时结束的可以采用候选 72 小时，须展示预计关闭时间及未解决入口。必须主动验收的保持待确认并单独计数。72 小时及具体准入需产品确认，默认留在人工确认路径。
2. 超时采用服务端工作进程的小批处理。截止时间随本次维修结果持久化，只有状态、版本、结果轮次和截止条件一致才处理。状态更新、系统事件及审计同事务，重试不重复，用户反馈与定时任务竞争时仅允许一次有效状态转换。区分本人确认、维修人员现场结单和系统超时关闭。
3. 反馈保持原工单上下文。对直接关闭或超时关闭的工单，在已告知的期限内允许本人提交未解决原因。若原维修人员仍启用、归属和类别匹配且无需换人则回到其处理中，原人明确不能继续时才进入待派单。保留已有维修、上门和审计历史。
4. 非白跑的过期时间窗在预约前应标明需要报修人更新，并允许有权限的维修人员发起一次重约请求；同一失效窗口不因重试重复生成待办。负责人和动作集中在原工单，不新增管理员催办队列。
5. 审核并派单作为后续可验证优化。管理员显式选人后一次确认，服务端同事务校验并记录审核与派单。人员变更失败回滚整次组合提交，仍可单独审核。

## Risks / Trade-offs

- 自动关闭容易被误解成报修人确认。区分关闭依据，展示反馈入口，主动验收和待解决异常排除在规则外。
- 同一维修人员继续处理可降低交接量，也可能掩盖确实需要换人的问题。明确显示继续处理人，保留有理由的改派。
- 统计、角色待办、历史及 MCP 对关闭依据和当前责任的表达需一起验收。用常规维修、必须验收、逾期无反馈、重复报障、重约等样例统计每个角色必须完成的操作次数。

## Migration Plan

先在独立环境用虚构工单验证。实际启用前确认适用条件、超时长度、反馈期限与可见性，限制到启用后新产生的合格结果。存量待确认工单没有自动截止日期。规则关闭后停止自动任务，对已产生的真实历史保留记录。

现有人工确认阶段，已关闭的复发通过关联的新报修审核。该入口保留原结单记录和来源维修记录。未来直接关闭或超时关闭的反馈期，仍按本提案评估原单恢复资格。
