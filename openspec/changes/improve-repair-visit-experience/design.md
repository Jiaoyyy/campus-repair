# Design

## Context

动机与边界见 proposal.md。已读取 README、handoff、原MVP proposal/design/tasks及 repair-work-orders/audit-evidence 规约。当前 model.go 的 transition 实现九种主状态，store.go 的 update 对工单加行锁，写事件及审计后提交；queue.go 和 presentation.ts 定义角色队列，main.tsx 集中列表与详情。订单 Input 只有类别、位置、描述，草稿复用创建幂等；目前没有预约表、上门事件或时间字段。

本轮依赖这些已实现契约，不依赖原MVP剩余AI/公网任务。主规约尚为空，采用独立新增能力；原任务完成率保持原样。

## Goals / Non-Goals

**Goals:** 让上门约定和异常成为可查询的真实数据；同一份服务端规则驱动详情、工作台和指标；人工流程在模型不可用时独立运行。

**Non-Goals:** 不重构为通用调度系统；不增加后台自动通知、自动状态流转或全流程SLA；不为上门安排扩展助手上下文和MCP数据面。

## Decisions

### 1. 独立上门生命周期，沿用主状态

采用 work_order_visit_context（一工单一行，保存时间偏好、有效预约ID、异常类型/原因/预计恢复时间及独立的再次上门标记）及 work_order_visits（每次确认预约一行，保存窗口、当前阶段及出发/到场/白跑时间、结束原因）。时间均存UTC，按Asia/Shanghai解释日期与展示。工单事件保留操作者、动作和说明，预约行提供结构化事实；两者同事务更新。

不增加主状态以避免破坏既有状态筛选、助手枚举和负载口径；不把自由文本处理记录当预约来源，否则无法可靠统计。预约阶段为scheduled/departed/arrived，结束后保留finished/voided/no_show结果。待备件与待重新约时作为context异常，不伪装结单。

旧单无context视为未安排；首次使用时懒创建。每次写入先锁work_orders，再锁context/visit，使用工单version串行化，与旧业务动作使用相同锁顺序。改派、重处理、取消、驳回、完成、确认在原业务事务中结束有效预约和清除当前异常，不抹掉旧历史。

### 2. 用户给偏好，维修人员确认

建单后显示可跳过的“补充方便上门时间”，不修改创建请求摘要、草稿提取字段或创建幂等键。只有本人能给偏好；接单人员在偏好内选择窗口，用户提前表达的可上门时间作为确认依据，不增加二次审批轮次。单个时间窗、未来14天、30分钟至4小时为本轮明确默认值，不声称是校方规定。

已出发/到场禁止本人修改偏好。需要调整时维修人员先记录真实异常：到场后no_show等待本人重新提供时间；waiting_parts撤销预约，填写未来预计恢复时间，之后resume写说明解除；如果此前仍有到场无人未解决，恢复后回到待重新约时，不能清除再次上门要求。no_show后只在本人重新提供时间、新预约到场后解除阻塞；resume仅用于waiting_parts；没有新预约的旧人工处理路径可继续，但不能绕过尚未解除的异常提交完成。预计恢复时间过期只显示“预计时间已过，请更新”，不自动恢复。

阶段动作：scheduled→departed→arrived；出发须预约结束时间未过，到场时间即服务端当前时间。已逾期且未出发需重新确认未来窗口；已出发后仍可到场并保留迟到事实。no_show仅arrived可做；waiting_parts允许任意处理中阶段，必须结束旧预约。

### 3. 普通业务接口与权限

拟新增：

| 接口 | 作用 | 写入主体 |
| --- | --- | --- |
| GET /api/work-orders/{id}/visit | 当前偏好、预约、异常、允许操作、读取时间 | 按原详情可见性 |
| PUT /api/work-orders/{id}/visit/availability | 保存/清除偏好，body含version/start/end/reason | 本人报修人 |
| POST /api/work-orders/{id}/visit/actions/{action} | schedule/depart/arrive/no-show/wait-parts/resume，body含version和必要字段 | 当前被指派维修人员 |
| GET /api/repair-workbench?view=… | 角色允许的队列、分页、全量计数、as_of | 维修人员/管理员 |
| GET /api/repair-workbench/metrics?date_from=…&date_to=… | 本组织协调数量、白跑事件计数及口径 | 管理员 |

沿用Bearer会话、400/403/404/409规则。拒绝未知动作与多余身份字段，验证内容长度（原因/说明最多2000字）和带时区时间，不能信任前端按钮。响应附最新工单版本；读取预约信息前先做工单可见性验证。

不增加新的写幂等记录：更新沿用version，重复旧版本为409。客户端遇未知结果先重读；已生效则展示结果，不自动再写。此语义与既有更新保持一致，可确保一次预约只记一次白跑。

### 4. 三端共用事实与队列定义

新增visits模块封装授权、动作校验和事务写入，避免继续扩大store.go；原update在关键状态动作调用同事务生命周期函数。查询统一用orderFilter和服务端as_of，单个工作台响应在一致性只读事务内生成当前队列计数与分页。统计依据spec中的事件和时间定义，不读取分页推算。

前端从main.tsx拆出VisitPanel、RepairWorkbench，复用ui.tsx和现有样式。维修角色登录优先工作台，报修人与管理员沿用原入口并加入详情预约卡/协调入口。查询错误、冲突和未保存保护沿用成熟模式。站内信息只随读取更新，不显示“已短信通知”或虚假的实时提醒。

### 5. 验收先验证闭环，再看指标

第一验收故事：报修→补时间→人工审核派单→接单→确认预约→出发→到场→维修结果→本人确认。
第二故事：到场无人→一次白跑→本人改时间→重新预约→最终修复。
第三故事：等待备件→预计恢复时间过期→人工恢复→继续处理。

每个故事加同组织他人、跨组织、旧指派、禁用/撤销会话校验；并发覆盖改时间/出发、预约/完成、异常/恢复。故障注入覆盖审计失败回滚、提交响应丢失、重启持久化。时间测试固定时钟，覆盖北京时间零点、到期等号边界与两个预约重复事件。模型断开时三故事仍能完成。

## Risks / Trade-offs

- [单个窗口不够灵活] → 第一版允许本人改时间，之后再考虑多候选窗口，不引入循环日历。
- [偏好不代表学校允许进入] → 全流程不提供无人进入授权；到场仅记录位置到达，不推导已入室。
- [白跑仅人工填报] → 标签明确“已记录白跑次数”，不推断责任或用于自动考核。
- [未记录预约的工单无法比较] → 不宣称全校白跑率或改善百分比；保留可选预约保证旧流程可用。
- [暂停异常被忽略] → 详情、工作台和完成接口统一检查异常，恢复有说明和事件。
- [旧镜像回滚不识别预约约束] → 启用前备份并记录迁移版本；回滚时暂停写入并恢复配套数据库与镜像，不能仅降级API后继续写。

## Migration Plan

1. 新增版本化建表与索引，基于work_order_id和有效预约查询建立索引；隔离验证老库升级、空库初始化及重复启动。
2. 先交付上门接口和事务钩子，再交付三端页面；不更改主状态值或既有创建字段。
3. 在独立*-check环境建立演示工单，完成三故事、越权、异常、并发、恢复及390px检查；日常不灌入测试工单。
4. 更新README、docs/api、docs/verification及handoff。保持真实网关未完成项不变。
5. 验证通过后按现有统一镜像流程更新API/worker/MCP/web，并核对实际镜像与ready。回滚使用实施前一致性备份，不删卷。
