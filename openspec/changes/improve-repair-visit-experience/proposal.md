# Proposal

## Why

现有系统能完成报修闭环，但接单后缺少上门时间约定，学生不知道何时需要在场，维修人员缺少按日安排和异常反馈入口。下一轮用预约、维修工作台和透明进度改善实际协作，为减少白跑提供可核对的过程数据，不依赖模型网关恢复。

## What Changes

- 报修创建后，本人可选填一个方便上门的时间窗；当前维修人员接单后确认其中的上门安排，双方在详情查看。
- 增加出发、到场、报修人不在、等待备件和恢复处理记录，明确下一处理方；业务主状态继续使用现有九种状态。
- 维修端默认展示待接单、待安排、今日上门和处理中入口，突出地点、时间、故障与主要操作。
- 报修人详情展示确认时间、当前上门阶段、异常原因和下一步；管理员获得预约逾期、待重新约时、待备件的协调队列。
- 基于真实预约和事件展示逾期数量、已记录白跑次数；先定义口径和验收证据，不承诺尚无试点数据支持的改善比例。

### Non-goals

本轮不做跨房间聚合、拍照识别、语音、照片结单、微信/短信/推送、无人进入授权、地图导航、路线优化、库存管理、新角色和 AI 自动操作。不增加模型或 MCP 写工具；不将预约超时等同于全流程 SLA 违约。

## Capabilities

### New Capabilities

- `repair-visits`：现有工单上的可选时间偏好、人工确认预约、上门阶段与异常、权限及事务契约。
- `repair-workbench`：三角色预约信息呈现、维修工作台、协调队列与准确统计。

### Modified Capabilities

无已归档主规约需要修改；`openspec list --specs` 当前为空。此变更依赖未归档的 `build-campus-repair-mvp` 已实现人工工单基线，新增要求独立存放；不复制或覆盖原变更，不视原变更为全部完成。现有状态、权限、待办和只读 MCP 契约继续有效；归档同步时先同步基线，再同步此变更。

## Impact

预计涉及 backend/internal/app 的 model/store/server/schema、角色队列及前端 main/api/presentation；增加独立上门数据与事件、普通业务接口、隔离验收脚本，更新接口与使用文档。创建接口、草稿三字段及原有助手工具参数保持兼容，上门时间在建单成功后补充。沿用 Go/MySQL/React 与现有鉴权，不新增外部服务。
