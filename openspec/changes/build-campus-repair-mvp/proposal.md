# Proposal

## Why

校园报修信息分散、字段缺失、处理过程难以追踪，管理员和报修人反复沟通。本项目建立可追溯的工单闭环，并通过受控 AI 辅助填写、查询和派单，交付符合课程工程及五项 AI 能力要求的独立互联网应用。

## What Changes

- 新建一个校区、照明/电器/给排水三类故障的首版应用，使用演示账号和模拟数据。
- 支持报修人、维修人员、后勤管理员登录与服务端组织/归属隔离。
- 实现提交、审核、补充、派单、改派、接单、维修记录、确认关闭、重新处理及取消。
- 建立维修知识库及异步索引，检索结果带可核对来源。
- 实现报修智能体与流式会话，提供信息补全、安全自查和派单辅助三项可启停技能。
- 使用真实 MCP Client/Server 执行受控只读查询，不向 AI 暴露任何业务写工具。
- 保存审计、接口与验收证据，提供持久化部署、备份恢复和公网入口。
- 分阶段实施：人工闭环优先；AI 接入其次；最终完成失败路径和部署验收。
- 人工阶段页面按角色区分待我处理、未结束和已结束工单；详情先展示当前责任、最新结果与主要操作，取消/改派作为次要入口，审计优先显示人员名称和工单编号。
- 统一整站字体、颜色、间距、控件和状态反馈；导航按业务与管理分组。助手以持续对话为中心，资料原文用侧栏核对；知识库采用紧凑列表，低频索引操作收起；助手设置分组并提供固定保存区。

- 对话式报修：报修人通过对话补全类别、位置与故障描述，在会话内编辑草稿卡片并主动确认；正常业务接口创建后返回真实工单编号和详情入口。草稿可取消、恢复，失败保留；AI 与 MCP 不获得写工具。

- 优化三角色多场景对话：授权工单概览、待办数量、状态/类别/今天筛选、编号定位、多轮筛选衔接、真实候选负载建议和带详情入口的结果卡片；区分实时查询与资料问答，失败不让模型猜数。

### Non-goals

不接入真实校方系统；不做付款、库存采购、校园 SSO、多校区运营、原生 App、自动派单或自动结单。图片附件、通知、复杂排班不是首版验收条件。不复制既有 CampusClaw 的代码、凭据、数据库或上传数据。

## Capabilities

### New Capabilities

- `identity-access`：Bearer 登录、撤销和到期、组织与三角色权限、账号管理边界。
- `repair-work-orders`：工单字段、状态转换、归属、指派、重试/并发和处理时间线。
- `repair-knowledge`：管理员材料管理、持久切片、异步索引、检索引用和失败恢复。
- `repair-assistant`：角色智能体、会话、三项技能、草稿确认及流式异常处理。
- `repair-mcp`：协议初始化与工具发现、绑定、只读鉴权调用及服务不可用处理。
- `audit-evidence`：业务与 AI 审计、最小统计、测试/贡献记录及证据留存。
- `application-delivery`：容器运行、持久化、异步任务恢复、密钥管理与公网部署。

### Modified Capabilities

无。此项目为新仓库，没有既有产品规约。

## Impact

新增 React/TypeScript 前端、Go API 与 MCP 服务、MySQL、Qdrant、Nginx 和 Compose 配置及自动化验收。服务端将调用兼容网关的嵌入和对话模型；具体凭据在实施时配置，不纳入仓库。数据库、工具、接口、页面和部署均为拟新增，不是当前存在的实现。

### 对话行为修正

移除所有角色对话中的检索算法选择，由服务端按问题和会话上下文决定资料查询。无命中不再跳过模型；支持自然交流、故障追问与多轮补充，缺少资料时不得编造制度、时限或实时人员/工单。资料依赖异常明确降级，保留正常对话和人工入口。

## 语义业务查询修正

增加模型原生 function calling 决策层，让模型结合本人已完成上下文选择只读查询或继续资料/草稿对话；位置、故障关键词、北京时间日期范围进入服务端白名单过滤。业务事实回答由实际成功查询结果生成，模型自由文本不能发布查询结论。

## Backend deployment consistency

API、worker、MCP使用同一后端镜像，避免仅重建API而MCP仍使用旧参数协议；部署验收比较实际镜像ID并执行日常只读查询，不以ready替代业务调用验证。

## Existing conversation stabilization

在真实网关暂停期间稳定现有对话：失败保留可编辑原问题和人工入口、流解析严格验证生命周期和分片、完成前授权复核后才发布正文；用模拟网关覆盖失败/停止/并发和跨角色隔离，不扩展新技能，不将模拟结果当真实验收。
